## FIX 1a - Function duration

Chosen value: 60 seconds.

Root vercel.json's `functions` block does NOT reach the built function for
this project. Verified empirically, not assumed:

1. Added a `functions` block to root vercel.json (`api/**/*.ts` glob,
   `maxDuration: 60`), rebuilt with `pnpm --filter @overlap/web build`, and
   inspected `.vercel/output/functions/__server.func/.vc-config.json`. It
   came out unchanged - no `maxDuration` key.
2. Read the Nitro "vercel" preset source
   (`node_modules/.pnpm/nitro@.../nitro/dist/_presets.mjs`,
   `generateFunctionFiles`/`resolveVercelRuntime`). It writes
   `.vc-config.json` by spreading `nitro.options.vercel?.functions` into a
   base object. The only place it reads the root `vercel.json` at all is to
   check `bunVersion`. There is no code path that merges vercel.json's
   `functions` glob config into the function this app builds.
3. This matches the Build Output API v3 docs
   (https://vercel.com/docs/build-output-api/primitives): `.vc-config.json`
   is the complete, self-contained spec for a function once a framework/build
   tool generates the Build Output API directory itself; nothing merges a
   root-level `functions` glob into it after the fact.

Reverted the vercel.json experiment (vercel.json is unchanged from before
this fix - `git diff vercel.json` is empty) and instead set the option where
it actually has effect: `apps/web/vite.config.ts`, in the `nitro({ preset:
'vercel', ... })` plugin config:

```ts
nitro({
  preset: 'vercel',
  vercel: {
    functions: {
      maxDuration: 60,
    },
  },
}),
```

Proof it landed, after a clean rebuild:

```
$ rm -rf apps/web/.vercel/output
$ pnpm --filter @overlap/web build
...
[nitro] ✔ You can deploy this build using npx vercel deploy --prebuilt

$ cat apps/web/.vercel/output/functions/__server.func/.vc-config.json
{
  "handler": "index.mjs",
  "launcherType": "Nodejs",
  "shouldAddHelpers": false,
  "supportsResponseStreaming": true,
  "maxDuration": 60,
  "runtime": "nodejs22.x"
}
```

Why 60s: the whole app (SSR pages, every `/api` route, both cron triggers)
builds into one `__server` function, routed via `.vercel/output/config.json`
(`{"src": "/(.*)", "dest": "/__server"}`), so there is exactly one duration
lever for the entire app. Pro/Fluid's platform default is already 300s, so
this is a deliberate reduction, not an extension. Every request this
function serves is meant to be fast: an SSR render, a handful of Drizzle
queries, at most one GitHub API call (diff fetch or OAuth token exchange), or
a `start()` call that hands off to a durable workflow run and returns
immediately without waiting on it. 60s leaves roughly 6x headroom over that
expected path while capping the cost/blast-radius of a genuine hang (a
wedged DB connection, an unbounded loop) to a fraction of the 300s default
instead of letting it run for 5-30 minutes.

```ts
  'use step'
```

```ts
export async function getActiveRepositoryIds(): Promise<{ repositoryIds: string[] }> {
  'use step'
  const repos = await db.query.repositories.findMany({ where: eq(repositories.isActive, true), columns: { id: true } })
  return { repositoryIds: repos.map((r) => r.id) }
}

export async function pruneRepositoryBranches(repositoryId: string): Promise<{ prunedBranches: number }> {
  'use step'
  // identical prune logic, scoped to exactly one repository
}
```

`apps/web/src/workflows/maintenance.ts`:

```ts
export async function pruneBranchesWorkflow(): Promise<{ prunedBranches: number }> {
  'use workflow'
  const { repositoryIds } = await getActiveRepositoryIds()
  let prunedBranches = 0
  for (const repositoryId of repositoryIds) {
    const result = await pruneRepositoryBranches(repositoryId)
    prunedBranches += result.prunedBranches
  }
  return { prunedBranches }
}
```

This mirrors `processWebhook`'s existing `syncInstallation` -> loop ->
`syncRepository` pattern exactly. The optional `repositoryId?` parameter
(never passed by any caller) was folded away rather than preserved. Updated
the misleading comment in `apps/web/src/routes/api/cron/prune-branches.ts`
that claimed the work "must not be bounded by a single function invocation"
while the code was in fact one function invocation covering every repo.

Pruning logic itself is byte-for-byte the same as the old loop body, just
un-indented one level and scoped to the single `repo` passed in.

## FIX 2 - postgres-js pool

`packages/db/src/client.ts`, `queryClient` only (migrationClient untouched
except a note added above both blocks):

```ts
const queryClient = postgres(connectionString, {
  prepare: false,
  max: 3,
  idle_timeout: 10,
})
```

- `max: 3`: a single warm instance never runs more than a couple of queries
  concurrently in this app (each request handler is a short, mostly
  sequential sequence of Drizzle calls). 3 gives headroom for that while
  keeping each instance's worst-case pooler footprint low. Since the
  exhaustion math is roughly `pooler_budget / max` concurrent warm instances
  before the pooler is saturated, dropping from the postgres-js default of
  10 to 3 raises the number of instances a fixed pooler budget can support
  by roughly 3x.
- `idle_timeout: 10` (seconds): releases connections back to Supavisor
  shortly after a burst of activity ends, instead of holding them open for
  the lifetime of the warm instance (which, on Fluid Compute, can be
  arbitrarily long). Idle instances stop costing pooler slots at all once
  their connections time out.

## FINDING 1 - `syncRepository` batching + `maxDuration` comment

### 1a. Batched writes in `apps/web/src/workflows/steps.ts`

Before, `syncRepository` had two sequential loops:

```ts
for (const remote of remoteBranches) {
  if (local) {
    if (local.sha !== remote.sha) {
      await db.update(branches).set({ sha, lastSeenAt, updatedAt }).where(eq(branches.id, local.id))
      updatedCount++
    }
  } else {
    await db.insert(branches).values({ ... })
    addedCount++
  }
}

for (const local of localBranches) {
  if (!remoteBranchNames.has(local.name)) {
    await db.update(branches).set({ lastSeenAt: new Date(0), updatedAt }).where(eq(branches.id, local.id))
  }
}
```

One DB round trip per branch, in both directions. For a repository with a few
thousand branches that is thousands of sequential round trips inside a single
step invocation, on top of the ~30 sequential paginated GitHub API calls
`getBranches` already makes (`per_page: 100`, `packages/github/src/client.ts`).

After, both loops are single set-based statements:

```ts
if (remoteBranches.length > 0) {
  await db
    .insert(branches)
    .values(remoteBranches.map((remote) => ({
      repositoryId,
      name: remote.name,
      sha: remote.sha,
      isDefault: remote.name === repo.defaultBranch,
      lastSeenAt: new Date(),
    })))
    .onConflictDoUpdate({
      target: [branches.repositoryId, branches.name],
      set: {
        sha: sql`excluded.sha`,
        lastSeenAt: sql`excluded.last_seen_at`,
        updatedAt: new Date(),
      },
      setWhere: sql`${branches.sha} <> excluded.sha`,
    })
}

const missingBranchIds = localBranches
  .filter((local) => !remoteBranchNames.has(local.name))
  .map((local) => local.id)

if (missingBranchIds.length > 0) {
  await db
    .update(branches)
    .set({ lastSeenAt: new Date(0), updatedAt: new Date() })
    .where(inArray(branches.id, missingBranchIds))
}
```

Behavior preservation, verified rather than assumed:

- `setWhere: sql`${branches.sha} <> excluded.sha`` makes the upsert's UPDATE
  side a no-op whenever the remote SHA matches what is already stored, which
  is what the old `if (local.sha !== remote.sha)` guard did - a branch whose
  SHA has not changed gets no write at all, not even a `lastSeenAt` bump.
  This is a real (if odd) piece of existing behavior that a naive
  unconditional upsert would have silently changed, and `setWhere` was
  chosen specifically to preserve it.
- `isDefault` is deliberately left out of the `onConflictDoUpdate` `set`
  clause, matching the old loop, which only set `isDefault` on the initial
  insert and never touched it again on update.
- Missing branches still get `lastSeenAt: new Date(0)` (epoch), exactly as
  before, via a single `inArray` UPDATE instead of one UPDATE per branch.
- `added`/`updated` counters: computed from the already-fetched
  `localBranches` (one `findMany`, unchanged from before) compared against
  `remoteBranches` (already fetched from GitHub), not from what the bulk
  statement reports touching. This means the counters did not need to trade
  precision for batching - they are exact, computed the same way the old
  loop counted them, just without an extra round trip. No precision was
  traded; noting this explicitly per the task's allowance to do so if
  needed.

**Verification against a real database.** The mocked unit tests in this repo
do not execute real SQL, so I could not rely on them to catch a syntax error
in the raw `sql`excluded.sha`` / `setWhere` pattern. I wrote a throwaway
script (not committed) using the same PGlite + real migrations setup the
integration test harness already uses
(`apps/web/test/integration/db-shim.ts`), seeded a repository with branches in
each of the four states the batching has to handle (unchanged, SHA-changed,
brand-new, vanished-from-remote), ran the exact statements above, and asserted
on the resulting rows. All four cases behaved identically to the old
per-branch loop:

```
main sha unchanged: true
unchanged branch lastSeenAt NOT bumped (should be 2020): true
will-change sha updated: true
will-change lastSeenAt bumped (should NOT be 2020): true
brand-new inserted: true
will-vanish lastSeenAt is epoch: true
row count (5 remote-ish + main, no dupes): 5
OK - no SQL errors, all assertions above should read true
```

The script and its build helper were deleted after the check; they are not
part of this commit.

### 1b. `maxDuration` comment in `apps/web/vite.config.ts`

The old comment justified 60s purely from the request path (SSR render,
Drizzle queries, one GitHub call, or a `start()` handoff). That reasoning
ignored that Vercel Workflow steps run as invocations of the same `__server`
function - stated explicitly at "A step is one function invocation" in
`apps/web/src/workflows/steps.ts` (in the `pruneRepositoryBranches` doc
comment) - so the 60s budget bounded every step too, including
`syncRepository`'s pre-1a per-branch loop.

Rewrote the comment to name workflow steps, specifically `syncRepository`, as
the dominant consumer of this budget, and to state what the worst-case step
looks like after 1a: the per-branch database loop is gone, so the dominant
remaining cost is the ~30-50 sequential paginated GitHub API calls a
multi-thousand-branch repository requires (`octokit.repos.listBranches` at
`per_page: 100`).

I raised `maxDuration` from 60 to **120**. At normal GitHub API latency, 30-50
sequential page fetches plus two bulk DB statements fit well inside 60s, but
I judged 60s too tight a margin against larger repositories or slower GitHub
responses to call it comfortably sized against the worst case rather than the
typical case - the task asked for a defensible ceiling, not a specific digit,
and explicitly permitted raising the value if 60 still seemed tight after 1a.
120s keeps roughly 2.5x margin under the 300s platform default, which still
bounds the blast radius of a genuine hang (wedged DB connection, unbounded
loop) to well under half the platform default, while giving the pagination
path real headroom instead of a number sized to a workload (many sequential
per-branch writes) that no longer exists in this function.

## FINDING 2 - `prune-repository-branches.test.ts` scoping assertions

Both flagged tests previously used `expect.anything()` for the `where`
condition (or, for `findMany`, never inspected the call args at all), so
deleting `eq(branches.repositoryId, repo.id)` from the `staleBranches` query
in `steps.ts` - which would make the step prune every stale branch fleet-wide
on every invocation - would not have failed either test.

`dbMock.query.branches.findMany`, render it to real SQL text + bound params
via `new PgDialect().sqlToQuery(...)` (the same dialect drizzle-orm's Postgres
driver uses internally), and compare against an independently-built expected
predicate using the same `and(eq(...), eq(...), lt(...))` drizzle helpers.
Both the "prunes exactly the one repository" test and the "falls back to the
default pruning window" test now do this, the second one with `vi.useFakeTimers`
+ `vi.setSystemTime` so the computed `staleDate` is deterministic and gets
compared against `DEFAULT_SETTINGS.PRUNING_DAYS` (14) rather than merely
asserting `findMany` was called once (true for any window value).
